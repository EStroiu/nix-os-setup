# NixOS Configuration

Personal NixOS configuration managed declaratively with **Nix flakes**, **Home Manager**, **Niri**, **Noctalia**, and Git.

The repository is designed so that:

* machine-specific configuration lives under `hosts/`;
* reusable system configuration lives under `modules/`;
* user configuration lives under `home/`;
* hardware configuration remains specific to each physical machine;
* the same shared setup can be reused across additional laptops;
* changes are tracked in Git and can be rolled back.

## Current desktop stack

The current laptop uses:

```text
NixOS
  ↓
greetd + tuigreet
  ↓
Niri
  ↓
Noctalia
```

User environment:

```text
Kitty
  ↓
Zsh
  ↓
Starship
```

GNOME and GDM are no longer part of the normal desktop setup.

# Configuration layout

## `flake.nix`

`flake.nix` is the entry point of the configuration.

It defines:

* the Nixpkgs revision used by the machines;
* Home Manager;
* flake dependencies;
* each NixOS host managed by this repository.

For example:

```nix
nixosConfigurations.personal-laptop-nixos = ...
```

represents the current laptop.

`flake.lock` pins exact dependency revisions and **must be committed to Git**.

This allows the same configuration to be reproduced later instead of silently pulling newer dependencies.

---

# `hosts/`

Each physical machine gets its own directory.

For example:

```text
hosts/
└── personal-laptop-nixos/
```

## `configuration.nix`

Contains configuration that describes that particular machine, including things such as:

* hostname;
* bootloader;
* imported modules;
* user account;
* login shell;
* Home Manager integration;
* system state version.

The goal is to keep this file relatively small.

Most reusable functionality belongs in `modules/`.

## `hardware-configuration.nix`

Generated by NixOS based on the hardware, partitions, filesystems, and detected devices of the machine.

This file is machine-specific.

Do **not** copy:

```text
hosts/personal-laptop-nixos/hardware-configuration.nix
```

to another computer.

Each new machine should use the `hardware-configuration.nix` generated by its own NixOS installation.

---

# `modules/`

Reusable operating-system configuration lives here.

## `common.nix`

Contains settings intended to be useful across machines, such as:

* flakes and modern Nix commands;
* NetworkManager;
* locale;
* timezone;
* common system utilities;
* package policy such as unfree package support.

This module should contain general system functionality rather than hardware-specific configuration.

## `desktop.nix`

Contains shared graphical-desktop infrastructure.

The current setup uses:

* `greetd` as the display/login manager;
* `tuigreet` as the login interface;
* Niri as the graphical session;
* PipeWire for audio;
* printing support;
* Firefox and other shared graphical-system functionality.

The startup path is:

```text
boot
 ↓
greetd
 ↓
tuigreet
 ↓
login
 ↓
niri-session
 ↓
Niri
 ↓
Noctalia
```

GNOME/GDM are no longer required as fallback desktop components.

## `niri.nix`

Enables the Niri Wayland compositor and its system-level requirements.

This includes components such as:

* Niri;
* Polkit support;
* keyring support;
* XWayland compatibility through `xwayland-satellite`;
* integration required for starting Niri through the login manager.

The actual Niri layout and keyboard configuration is kept under Home Manager in:

```text
home/remarka/niri/config.kdl
```

## `maintenance.nix`

Configures automatic Nix maintenance.

The current policy is approximately:

```text
garbage collection: weekly
delete generations older than: 14 days
store optimisation: weekly
```

Systemd-boot is also configured to keep a limited number of boot configurations.

The current target is:

```text
10 boot generations
```

These are related but separate concepts:

```text
boot configuration limit
    ↓
limits entries shown/installed in /boot

garbage collection
    ↓
deletes old generations and unreachable Nix store paths
```

## `ssh.nix`

Enables the OpenSSH server.

This allows the laptop to be accessed remotely through SSH.

Root SSH login should remain disabled.

Private SSH keys are **not** stored in this repository.

## `wireguard.nix`

Provides WireGuard tooling.

NetworkManager is used to manage laptop VPN connections.

Private WireGuard profiles and keys should remain outside Git.

For example, a local profile can be imported with:

```sh
nmcli connection import type wireguard file ~/Downloads/example.conf
```

# `home/`

User-specific configuration is managed with Home Manager.

Current user:

```text
home/remarka/
```

## `home.nix`

Contains the personal user environment.

This includes things such as:

* Zsh;
* Starship;
* Kitty;
* Git configuration;
* CLI utilities;
* fonts;
* launcher/shell utilities;
* personal application configuration.

The general rule is:

```text
NixOS modules
    → machine and system services

Home Manager
    → personal applications and user configuration
```

## Terminal stack

The current terminal stack is:

```text
Kitty
  ↓
Zsh
  ↓
Starship
```

Kitty uses JetBrains Mono for terminal text.

Its unnecessary client-side titlebar is hidden, which works particularly well with a tiling compositor such as Niri.

Starship is configured as a single-line prompt rather than placing the prompt character on another line.

## `niri/config.kdl`

Contains the user-level Niri configuration.

Home Manager installs it as:

```text
~/.config/niri/config.kdl
```

It contains:

* Niri keyboard shortcuts;
* column navigation;
* vertically stacked windows;
* window resizing;
* workspaces;
* multiple-monitor controls;
* Overview;
* Noctalia integration;
* Kitty launcher;
* fullscreen/floating controls.

---

# Niri concepts

Niri uses a scrolling layout based on **columns**.

A useful mental model is:

```text
workspace
└── columns arranged horizontally
    └── one or more windows stacked vertically
```

Therefore:

```text
left / right
    → move between columns

up / down
    → move between windows stacked in a column

workspace up / down
    → move between separate workspaces
```

## Important shortcuts

The current configuration includes shortcuts along these lines:

```text
Super + Enter
    Open Kitty

Super + Space
    Noctalia application launcher

Super + S
    Noctalia control center

Super + Shift + /
    Niri shortcut help

Super + O
    Niri Overview

Super + Q
    Close window
```

### Column navigation

```text
Super + Left / Right
    focus adjacent column

Super + Ctrl + Left / Right
    move current column left/right
```

### Vertically stacked windows

```text
Super + Up / Down
    focus windows within current column

Super + Ctrl + Up / Down
    reorder windows vertically
```

Windows can be consumed into a column or expelled back into their own column.

### Height

The Niri configuration supports:

```text
50% window height
100% window height
manual height increase/decrease
preset height cycling
automatic-height reset
```

This is useful when placing multiple terminals or applications vertically in one column.

### Workspaces

Workspace navigation deliberately uses a different modifier combination so it does not conflict with vertical navigation inside a column.

# Normal configuration workflow

Enter the repository:

```sh
cd ~/nixos-config
```

After modifying existing files or adding new ones:

```sh
git add .
```

This step is especially important when creating **new files**.

Git-backed flakes do not expose untracked files to Nix.

For example, if this file exists:

```text
modules/example.nix
```

but has not been staged, Nix may report:

```text
Path 'modules/example.nix' is not tracked by Git
```

Run:

```sh
nix flake check
```

Then apply the configuration:

```sh
sudo nixos-rebuild switch \
  --flake ~/nixos-config#personal-laptop-nixos
```

If the configured Zsh `rebuild` alias is available, the shorter command is:

```sh
rebuild
```

After verifying that the system works:

```sh
git status
git commit -m "Describe the change"
git push
```

A typical workflow is therefore:

```text
edit
 ↓
git add .
 ↓
nix flake check
 ↓
rebuild
 ↓
test
 ↓
git commit
 ↓
git push
```

# Build without activating

When making a potentially risky change, build first:

```sh
sudo nixos-rebuild build \
  --flake ~/nixos-config#personal-laptop-nixos
```

If it succeeds, apply it:

```sh
sudo nixos-rebuild switch \
  --flake ~/nixos-config#personal-laptop-nixos
```

For changes to the login manager or other boot-sensitive components, it can be safer to install the configuration for the next boot:

```sh
sudo nixos-rebuild boot \
  --flake ~/nixos-config#personal-laptop-nixos
```

Then reboot manually.

# Updating NixOS and Home Manager

Updates are kept intentional rather than silently changing the system automatically.

Update flake inputs:

```sh
cd ~/nixos-config
nix flake update
```

Stage the modified lock file:

```sh
git add .
```

Check the resulting configuration:

```sh
nix flake check
```

Build/apply:

```sh
sudo nixos-rebuild switch \
  --flake ~/nixos-config#personal-laptop-nixos
```

After verifying the updated system:

```sh
git add .
git commit -m "Update flake inputs"
git push
```

This makes dependency updates visible in Git history.

# Garbage collection and generations

List NixOS generations:

```sh
nixos-rebuild list-generations
```

Inspect maintenance timers:

```sh
systemctl list-timers | grep -E 'nix-gc|nix-optimise'
```

Manual garbage collection can be run with:

```sh
sudo nix-collect-garbage --delete-older-than 14d
```

Normally this should not be necessary because automatic maintenance is configured.

# Rollback and recovery

There are two useful recovery mechanisms.

## NixOS boot generations

If the latest configuration fails badly, reboot and select an older NixOS generation from the systemd-boot menu.

The system deliberately keeps several generations for this reason.

## Git

Configuration changes are tracked through Git.

To inspect history:

```sh
git log --oneline
```

A previous known-good commit can be checked out or restored if required.

Git rollback and NixOS generation rollback solve slightly different problems, so keeping both is useful.

# `.gitignore`

The repository ignores generated/local files such as:

```text
result
result-*
.direnv/
.env
editor temporary files
```

The `result` symlink created by:

```sh
nixos-rebuild build
```

may still physically exist in the repository directory.

That is expected.

`.gitignore` tells Git to ignore it; it does not prevent Nix from creating the symlink.

If `result` was accidentally committed before being added to `.gitignore`, remove it from Git tracking with:

```sh
git rm --cached result
```

# Adding another NixOS machine

Suppose the new machine will be:

```text
work-laptop-nixos
```

## 1. Install NixOS normally

Perform a normal NixOS installation first.

Confirm that the machine boots before replacing its configuration with this repository.

## 2. Clone the repository

```sh
git clone git@github.com:EStroiu/nix-os-setup.git ~/nixos-config
cd ~/nixos-config
```

## 3. Create the new host

```sh
mkdir -p hosts/work-laptop-nixos
```

## 4. Copy that machine's generated hardware configuration

```sh
sudo cp /etc/nixos/hardware-configuration.nix \
  ~/nixos-config/hosts/work-laptop-nixos/hardware-configuration.nix
```

Fix ownership if necessary:

```sh
sudo chown "$USER":"$(id -gn)" \
  ~/nixos-config/hosts/work-laptop-nixos/hardware-configuration.nix
```

Never reuse another machine's `hardware-configuration.nix`.

## 5. Create its host configuration

Create:

```sh
nano hosts/work-laptop-nixos/configuration.nix
```

A new laptop can reuse the existing modules:

```nix
{ pkgs, ... }:

{
  imports = [
    ./hardware-configuration.nix

    ../../modules/common.nix
    ../../modules/desktop.nix
    ../../modules/niri.nix
    ../../modules/maintenance.nix
    ../../modules/ssh.nix
    ../../modules/wireguard.nix
  ];

  boot.loader.systemd-boot = {
    enable = true;
    configurationLimit = 10;
  };

  boot.loader.efi.canTouchEfiVariables = true;

  networking.hostName = "work-laptop-nixos";

  users.users.remarka = {
    isNormalUser = true;
    description = "Elena Stroiu";

    extraGroups = [
      "networkmanager"
      "wheel"
    ];

    # Use the same login shell configured for the current setup.
    shell = pkgs.zsh;
  };

  home-manager = {
    useGlobalPkgs = true;
    useUserPackages = true;

    users.remarka = import ../../home/remarka/home.nix;
  };

  system.stateVersion = "26.05";
}
```

The exact boot configuration may need to change for different hardware.

Do not copy `system.stateVersion` blindly if the new machine was first installed using a different NixOS release. Use the value generated for that installation.

## 6. Add it to `flake.nix`

Add another configuration:

```nix
nixosConfigurations.work-laptop-nixos = nixpkgs.lib.nixosSystem {
  system = "x86_64-linux";

  modules = [
    ./hosts/work-laptop-nixos/configuration.nix
    home-manager.nixosModules.home-manager
  ];
};
```

The repository then becomes:

```text
hosts/
├── personal-laptop-nixos/
└── work-laptop-nixos/
```

while both machines can reuse:

```text
modules/
home/remarka/
```

## 7. Stage new files

```sh
git add .
```

This is mandatory before flakes can see newly created host files.

## 8. Check the flake

```sh
nix flake check
```

## 9. First build

```sh
sudo nixos-rebuild build \
  --flake ~/nixos-config#work-laptop-nixos
```

If successful:

```sh
sudo nixos-rebuild switch \
  --flake ~/nixos-config#work-laptop-nixos
```

If flakes are not yet enabled on the freshly installed machine, the initial rebuild can temporarily enable the required features:

```sh
sudo nixos-rebuild switch \
  --flake ~/nixos-config#work-laptop-nixos \
  --option experimental-features "nix-command flakes"
```

After the shared configuration is active, flakes are enabled declaratively.

# What should be shared?

Good candidates for shared configuration:

```text
modules/common.nix
modules/desktop.nix
modules/niri.nix
modules/maintenance.nix
modules/ssh.nix
modules/wireguard.nix
home/remarka/
```

Machine-specific configuration normally includes:

```text
hardware-configuration.nix
hostname
boot configuration
GPU configuration
machine-specific drivers
disks/filesystems
machine-specific services
```

If machines eventually need substantially different roles, create additional modules instead of filling host configurations with conditionals.

For example:

```text
modules/
├── common.nix
├── development.nix
├── gaming.nix
├── work.nix
└── ...
```

A host can then import only what it needs.

# Secrets

Do not commit plaintext secrets.

This includes:

* SSH private keys;
* WireGuard private keys;
* VPN configuration containing credentials;
* Wi-Fi passwords;
* API tokens;
* passwords.

SSH private keys should remain under:

```text
~/.ssh/
```

WireGuard profiles containing private keys can remain managed locally by NetworkManager.

If reproducible secret management becomes necessary, use an encrypted solution such as:

```text
sops-nix
```

or:

```text
agenix
```

`.gitignore` should not be treated as a security mechanism for secrets.

# Design principle

The basic architecture is:

```text
flake.nix
    dependencies and machines

hosts/
    individual physical machines

modules/
    reusable NixOS/system configuration

home/
    reusable user configuration
```

The goal is deliberately **not** to build a highly abstract Nix framework.

A new laptop should mostly require:

```text
new hardware-configuration.nix
+ small host configuration
+ existing shared modules
+ existing Home Manager configuration
```

Only introduce additional abstraction after real duplication appears.

This keeps the setup understandable, reproducible, and easy to debug.
